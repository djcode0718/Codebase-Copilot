## 1. Executive Summary

This report documents the final stabilization pass of the Codebase-Copilot retrieval architecture. Following forensic audits (`FINAL_METRICS_VALIDATION_REPORT.md`), three targeted improvements were implemented and evaluated alongside the validated provisional retrieval configuration:

1. **CrossEncoder Metadata Injection**: Prepending relative file paths and code symbols directly into document text presented to the CrossEncoder reranker.
2. **Dynamic Candidate-Grounded Entity Verification**: Ensuring technology/framework queries are verified dynamically against retrieved candidate chunks and isolated repository metadata without static keyword blacklists.
3. **Resolution of Documentation Priority Inversion**: Eliminating the artificial 2-chunk code ceiling for code-lookup queries when strong implementation evidence is present, preserving both documentation and code by empirical relevance.

## 3. Implementation Details for Approved Fixes

### Fix A: CrossEncoder Metadata Injection
- **Problem**: When a user queried a specific file or symbol (e.g., `compare/predict_single_image.py`), the CrossEncoder only saw the raw document text. General `README.md` files mentioning `predict_single_image.py` systematically scored higher than the actual implementation because READMEs are high-level and token-dense.
- **Implementation**: In [`app/retrieval/reranker.py`](file:///Users/sj/Documents/AI-Copilot/codebase-copilot/app/retrieval/reranker.py#L150-L172), extracted `path` and `symbol_name` from node metadata:
  ```python
  header_parts = []
  if path and not txt.startswith("File:") and not txt.startswith(f"[{path}]"):
      header_parts.append(f"File: {path}")
  if symbol and f"Symbol: {symbol}" not in txt:
      header_parts.append(f"Symbol: {symbol}")
  if header_parts:
      doc_text = f"{header}\n\nContent:\n{txt}"
  ```
  The document text was capped at 4,000 characters to prevent tokenizer overflow.
- **Result**: Code files are immediately distinguishable by the reranker. For example, `EXP-FSX-07` ("Show the implementation of compute_dice in compare/compare_baselines.py") shifted from an unranked miss to a Rank-1 hit.

### Fix B: Dynamic Candidate-Grounded Entity Grounding
- **Problem**: Static keyword filters reject queries simply because words like "react", "kafka", or "redis" appear in the prompt, falsely rejecting valid questions in repositories that actually use those technologies (e.g., NeuroVera uses Next.js/React).
- **Implementation**: In [`app/retrieval/orchestrator.py`](file:///Users/sj/Documents/AI-Copilot/codebase-copilot/app/retrieval/orchestrator.py#L230-L315):
  - Uses `_verify_framework_grounding` to dynamically inspect evidence rather than blindly rejecting queries.
  - Dynamically builds an isolated evidence corpus from `nodes`, `candidate_nodes` (dense + BM25 pool), and target repository manifest files (`package.json`, `requirements.txt`, `pyproject.toml`, etc.).
  - Enforces repository isolation: only manifests and candidate chunks belonging to the targeted repository are searched.
  - Returns `(False, message)` triggering Tier 4 abstention only when the requested technology is unsupported by the target repository.
  - *Scope Note*: Verification is triggered for 14 target frameworks defined in `TECH_CHECKS` (`postgresql`, `redis`, `kafka`, `rabbitmq`, `celery`, `graphql`, `mongodb`, `docker`, `kubernetes`, `fastapi`, `django`, `flask`, `react`, `vue`). Queries involving technologies outside this dictionary rely on the standard confidence threshold floor.
- **Result**: Valid questions about React in NeuroVera are accepted, while questions about Redis/Kafka in repositories that lack them are properly abstained.

### Fix C: Resolution of Documentation Priority Inversion
- **Problem**: Previously, if Tier 2 documentation confidence exceeded Tier 3 code confidence by any margin, Tier 2 took precedence and code chunks were hard-capped at at most 2 chunks: `final_nodes = doc_nodes + [n for n in code_nodes[:2]]`. For explicit code lookup queries, 3 or 4 documentation chunks displaced the actual implementation code.
- **Implementation**: In [`app/retrieval/orchestrator.py`](file:///Users/sj/Documents/AI-Copilot/codebase-copilot/app/retrieval/orchestrator.py#L555-L590):
  - For `QueryMode.CODE_LOOKUP`: when code chunks have valid evidence, they are never artificially capped at 2.
  - Nodes in `reranked_nodes[:TOP_K_RERANK]` populate `final_nodes` by empirical CrossEncoder relevance score.
  - Documentation chunks remain available when they genuinely answer the query (e.g., usage examples or README-only questions).
  - For `QueryMode.ARCHITECTURAL`: architecture summary nodes are preserved at the top while strictly adhering to the configured Top-5 budget (`arch_nodes + semantic_nodes[:max(0, TOP_K_RERANK - len(arch_nodes))]`).
- **Result**: Implementation chunks dominate code lookup results (61.5% code vs 27.9% doc in final context), while documentation remains available for conceptual and installation questions.

## 9. Remaining Limitations and Known Failures

1. **Unindexed Binary and Checkpoint Artifacts**:
   - Queries referencing models defined purely in PyTorch weight files (e.g., CamouflageSegNet checkpoints in `FedSegX`) or raw datasets (`output10.wav`) cannot be resolved purely from source AST. This is an indexing coverage boundary, not a retrieval pipeline defect.
2. **Sub-component Architectural Reasoning Latency**:
   - Queries that require multi-hop reasoning across 3+ modules still average ~4.5 seconds per query due to CrossEncoder scoring depth (15 pairs).
3. **Single Unsupported False Acceptance in NeuroVera**:
   - Query `EXP-NV-19` ("How is Celery distributed task queue configured?") produced a modest score because NeuroVera has internal task scheduling functions (`task_runner.py`), although Celery itself is not used.
4. **Static Framework Trigger Scope (`TECH_CHECKS`)**:
   - `_verify_framework_grounding` monitors a fixed internal dictionary of 14 frameworks (`TECH_CHECKS`). External technologies outside this dictionary (e.g. Cassandra, ClickHouse, Snowflake, Temporal) do not trigger dynamic manifest/corpus grounding, relying entirely on raw vector/BM25 confidence floors to abstain.
5. **Repository Isolation Propagation Contract & Unlabelled Chunks**:
   - The isolation contract relies on the caller supplying an authenticated `target_repo_id` (derived from the validated Supabase session). If a caller omits `target_repo_id`, the orchestrator falls back to `resolve_repository_id(index_name)`. When `target_repo_id` is supplied, it is strictly validated against `canonical_repo_id` and enforced across all candidate and reranked nodes.
   - *Metadata Stamping Limitation*: Because initial document loading (`load_documents`) does not stamp `repository_id` into node metadata at embedding time, `enforce_chunk_isolation` currently operates in non-strict mode (`require_existing_metadata=False`), stamping `target_repo_id` dynamically onto chunks from the verified collection. Enforcing strict metadata isolation (`require_existing_metadata=True`) will require stamping repository UUIDs into Chroma at indexing time in `app/indexing/index_builder.py`.
